# 面试讲解提纲

## 30 秒版本

我做的是一套企业知识库 RAG 与只读运维 Agent。底层基于 Onyx，但我不仅完成了部署，还构建了企业仿真知识库，并接入真实 GitHub 仓库的文档、Issue 和 PR；我建立了自动评测体系，对中文 Embedding 做 A/B 优化，并自行开发受鉴权的只读诊断 API。最终 CloudOrder 检索 Hit@5 达到 100%、MRR 为 0.866，真实 GitHub 20 题评测的来源命中、可回答题引用和拒答均达到 100%。

## 3 分钟版本

### 1. 为什么做

普通聊天 Demo 只能证明模型 API 能调用，不能回答企业落地中的数据接入、召回质量、幻觉、安全、部署和运维问题。我希望做一套能量化和持续优化的企业 LLM 应用。

### 2. 系统结构

- Onyx 负责聊天、Agent、知识连接器和检索编排。
- DeepSeek V4 Flash 负责答案生成。
- Multilingual E5 在 CPU 上生成中文向量。
- OpenSearch 承担混合检索，PostgreSQL 保存配置和业务元数据，Redis 处理缓存和任务，MinIO 保存文件。
- 自研 CloudOrder Ops API 提供只读订单、支付回调和事件诊断，通过 OpenAPI Action 供 Agent 调用。
- GitHub Connector 每 6 小时增量同步 `macrozheng/mall`，真实数据与 CloudOrder 仿真数据分别绑定独立文档集和 Agent。

### 3. 如何评测

我为 CloudOrder 构造了 50 道带标准来源的黄金问题，记录 Hit@5、MRR 和延迟；另选 10 道高风险问题验证引用、拒答和答案忠实度。接入真实 GitHub 后，又建立 20 题独立评测集，覆盖文件、Issue、PR、多来源推理和安全拒答。这样每次修改 Prompt、Embedding 或数据源都能回归，而不是凭主观感受判断。

### 4. 做过的优化

Nomic 基线 Hit@5 是 95.8%、MRR 是 0.797。更换 multilingual-e5-base、完成正确的全量重建后，Hit@5 提升到 100%、MRR 提升到 0.866，P95 降至 0.783 秒。

### 5. 最难的问题

更换 Embedding 后，Onyx 任务显示 SUCCESS，但检索返回 0 文档。我没有直接归因于模型，而是检查数据库中的索引任务，发现扫描了 30 份文档但 `new_docs=0、total_chunks=0`。强制 from_beginning 仍被文件去重跳过，最后通过原位替换文件 ID 触发重新摄取，确认写入 30 chunk 后再评测。

### 6. Agent 安全

最初暴露多个底层工具时，模型会自行拼接结果并增加不可靠建议。我把模型可见工具收敛为一个 `diagnoseOrder` 聚合接口，底层接口只留给人工；同时要求先检索精确 Runbook、禁止跨 Runbook 搬阈值，并固定披露“只读查询、未修改数据”。

### 7. 真实数据评测中的误差分析

第一次 Mall 评测中，拒答答案实际正确，但关键词评分器误判；同时一题把 `dev_flow.md` 错当成“开发流程”，核对原文后发现它实际是“功能完成进度”。我扩充拒答判定表达，并修正黄金问题的事实定义，再做针对性复测和全量回归。最终 20 题请求、来源命中、可回答题引用与拒答均达到 100%。这个过程保留了失败报告，没有用修改指标的方式掩盖问题。

### 8. 性能和容量

我把检索和完整 Agent 分开压测。纯检索最高验证到 32 并发，成功率 100%、P95 0.94 秒；完整 Agent 在 6 并发突发下成功率 100%、P95 15.44 秒。压测期间服务器仍有约 21GB 可用内存，因此瓶颈不在内存，而在生成/编排延迟以及高并发下的 API Server、OpenSearch。基于短时测试，我给单实例设置了 4 个常规并发、6 个短时突发的保守建议，并强调这不是生产 SLA。

### 9. CI/CD 与回滚

CI 在每次提交和 Pull Request 上执行 API 单测、评测脚本编译、70 道黄金问题结构校验、凭据扫描和受限容器冒烟。CD 不在生产服务器现场安装依赖，而是在 GitHub Runner 构建镜像，经 `production` Environment 人工审批后上传；服务器加载镜像、保留旧镜像标签并等待健康检查，失败则恢复旧源码和镜像。这样将“代码正确”“制品可运行”和“允许上线”分成三个门禁。

## 高频追问

### 为什么不用纯向量检索？

企业文档同时存在语义问题和精确标识符，例如订单状态、事件名和错误码。混合检索可以结合语义召回与关键词精确匹配，降低单一检索方式的盲区。

### Hit@5 和 MRR 有什么区别？

Hit@5 只判断正确文档是否出现在前五；MRR 还衡量正确文档排得是否靠前。两者一起看，既能判断是否召回，也能判断排序质量。

### 为什么换成 multilingual-e5-base？

语料以中文为主。先保留 Nomic 基线，再只替换 Embedding、固定其他变量，通过同一套 50 题验证。最终 E5 在召回、排序和 P95 上都更好，所以不是凭模型名选择。

### 如何减少幻觉？

从三层处理：检索层提高召回；Prompt 层要求事实问题强制检索和无来源拒答；工具层缩小能力面并返回结构化事实。最后用无答案题、敏感问题和冲突文档做回归。

### 为什么工具只读？

大模型输出具有不确定性。查询类操作风险可控，而补偿支付、修改订单等操作需要审批、双人复核和审计。当前项目刻意将 Agent 限制在建议与只读诊断层。

### 项目目前还有哪些不足？

目前已接入 674 条真实 GitHub 数据并验证增量同步，但尚未完成 HTTPS、COS 异地备份、完整可观测平台和并发压测；公开数据规模也不能等同于企业私有海量语料。因此我将它定义为企业工程化 MVP，而不是已经投产的系统。
